# AsterCorpus-v0 仕様案

状態：初回提案。2026-09-15。配合・生成器・学習器は未検証。

2026-09-20方針更新：日本語は自作文に加え、ユーザー選定の外部文章・AI対話も候補に含める。
以下の配合は初回仮説を保持する。「ユーザーの文章」はユーザー著作に限定せず、選定した素材を含む。
選定者と著者を区別し、出典は `source-notes-v0.json`、採用調査は `selection-review-v0.md` に記録する。
読む素材と応答模倣の素材を区別し、外部対話をそのままAsterの標準口調の教師にしない。

## 1. v0で確かめること

自作日本語、外部Math/Python、自作の構造化データを、追跡可能な一つの学習セットにする。
まず固定したrecipeで単純なBPEとTinyLMを評価し、その観測からv0.1を決める。
この小規模セットだけで広い数学能力、日本語での数学説明、汎用Agent能力が得られるとは仮定しない。

## 2. 初回の配合

量の単位は**学習本文のUTF-8 bytes**。Tokenizerによって量の定義が変わらず、準備時に測れるため。
同じbytesでも日本語と英語の文字数は異なる。BPE後には領域別の文字数とtoken比率も報告する。

| 領域 | 目標比率 | 合計256 KiBの場合 | 内容 |
| --- | ---: | ---: | --- |
| ja_prose | 30% | 約77 KiB | ユーザーの散文・説明 |
| ja_dialogue | 20% | 約51 KiB | ユーザーの複数ターン会話 |
| math | 20% | 約51 KiB | 英語の問題＋解答 |
| python | 20% | 約51 KiB | 英語教材＋コードと出力 |
| aster_structured | 10% | 約26 KiB | 自作JSON・toolエピソード |

これは能力上の最適値ではなく、日本語を半分残す初期仮説。
256 KiBは動作確認を兼ねた開始目安で、TinyLMの十分な学習量を意味しない。
日本語の量が少なければ総量を縮める。穴を外部日本語や大量の反復で埋めない。
各領域を分割した後、trainだけから固定seed `20260915` による順序で完全な文書を選ぶ。
各領域は予算を超える文書を飛ばして次へ進み、最後に実量と目標との差を記録する。重複補充はしない。
予算不足があれば総量・配合を再決定してから凍結する。dev/testは配合調整で選別しない。

## 3. 原本から学習入力へ

2026-09-20自動化更新：canonical候補は台帳とpoolから直接生成する。
currentへのコピーを変換の前提にせず、採用・分割・配合を経た学習用viewはtrainingへ置く。
詳細と実装済み範囲は [canonical-v0.md](canonical-v0.md) を参照。
以下のcurrent→Tokenizer直結は初回案。新pipelineではcanonicalのJSONLを直接Tokenizerへ渡さない。

原本は `data/raw/pool/`、整理・選別した採用本文は `data/raw/current/` に置く。
currentではtrain/dev/testを分け、Tokenizerの学習にはtrainだけを渡す。
既存CLIの `--canonical-dir` でtrainを指定できるが、整形・分割処理は未実装。
poolの原本を残し、currentの採用一覧と本文hashで実験時の版を固定する。

日本語の最初の目安はprose 10本×300〜500字、dialogue 10会話×200〜400字（会話全体）。
合計5,000〜9,000字で動作確認と観察を始め、次に合計2〜5万字を目指す。
これは作業量の目安で、モデル性能を保証する量ではない。
独立した話題や目的を増やし、同じ原稿を細分化して件数を稼がない。

1. 原本と権利表示を保存し、URL、revision、取得時刻、SHA-256を記録。
2. UTF-8として読む。改行はLFへ統一し、NUL・不正UTF-8・空文書は除外する。
3. Pythonのインデント・文字列、数学記号を保持。NFKC、全角半角変換、空白の一括圧縮を行わない。
4. 問題＋解答、会話全体、教材の節を一単位にする。途中切断はしない。
5. 重複と近似重複をまとめ、元文書・派生関係ごとのgroupを決めてから分割。
6. train/dev/testと出典を確定し、trainの本文だけをTokenizerに渡す。

保管レコードは既存の `id / text / source` を保持し、別の索引で
`domain, language, upstream_id, source_revision, license, raw_sha256, transform_version,
group_id, split, text_sha256, generator_version, seed, verifier_version, verification_status`
を管理する案。外部資料には生成器関連の値はnull。
メタデータやライセンス全文を学習本文に混ぜない。
索引と本文を接続する処理はこれから実装する。

## 4. 分割

- 公式分割がある場合は尊重する。GSM8Kの公式testは学習・Tokenizer・日常調整から隔離する。
- 公式trainから、group IDのSHA-256先頭8桁を整数化して `% 100` が0〜9ならdev、その他をtrainとする。
- 公式分割のない著作文・教材・自作生成は、同じ方法で0〜9をtest、10〜19をdev、20〜99をtrainとする。
- Python教材は章をgroupにする。章数が少ないため、分割が空なら凍結前に章の割当を明示して固定する。
- 自作生成はテンプレート族をgroupにする。同じ式で数字だけ変えたものを未知課題と数えない。
- 翻訳、言い換え、同じ問題の別解、同じ会話のターンは同一group。
- 完全一致を本文hashで調べる。問題文・コードの近似一致候補も確認し、分割を跨ぐ候補は隔離する。
- 小さすぎてdev/testが成立しない場合は「配線確認用」と表示し、汎化評価を主張しない。

## 5. Asterが作るstructured / JSON / tool

### 初期：Asterプロジェクトが生成する

未学習TinyLMに正解データを作る能力を前提にしない。
まず小さな決定的生成器と検証器を実装し、由来を `programmatic` と記録する。
これは将来のモデル自身による生成に向けた足場である。

最初の10%枠では、JSON形式30%、単一tool実行50%、記録の書き込み→読み出し20%を目安にする。
大量の種類を作らず、JSONの基本型、整数計算器、エピソード内のkey-value記録に絞る。

- JSON：object、array、string、number、boolean、null。日本語、引用符、改行、空配列を含める。
- 計算器：`add/sub/mul` と小さな整数引数。実行器が計算し、モデルへ観測を返す。
- 記録：`memory.put/get`。書いた値を後の行動で読む。エピソード間の状態は初期段階では分離する。
- 正常例に加え、未知のkey・引数の型違いを作り、観測後の修正または適切な終了を含める。
- 不要な道具を呼ばず直接答える対照例を含め、呼び出し回数自体を目標にしない。

エピソード例（説明用。実行済みデータではない）：

```json
{"role":"user","content":"17と25を足して"}
{"role":"assistant","tool_call":{"name":"calculator","arguments":{"op":"add","a":17,"b":25}}}
{"role":"tool","name":"calculator","result":{"value":42}}
{"role":"assistant","content":"42です。"}
```

上の日本語は形式を示す説明例。実際の自然言語テンプレートはユーザーの表現を受け取って固定する。
tool行は必ず実行器が書く。検証はJSON構文、引数schema、実行結果、最終応答の一致を別々に判定する。
保存用JSONL全体を無条件で学習するのではなく、LM学習時はrole境界とloss対象を明示する。
tool運用の追加学習ではassistantの呼び出し・応答を予測対象にし、tool結果は入力条件として扱う案。

### 将来：Asterモデルが提案し、外部で検証する

`課題 → Asterの提案 → 実行 → 検証 → 採用/不採用の記録 → 次版へ`

モデル版、親データ、seed、実行ログ、検証器版、失敗理由を残す。
自己採点だけで採用しない。成功例だけでなく失敗率と重複率も記録する。
評価問題から生成した派生はtrainへ戻さない。自動生成を凍結済みv0へ追記しない。
永続的な記憶・道具の作成と改良は、その後に別実験として広げる。

## 6. Tokenizer / TinyLMでの評価

**Tokenizer**：まず既存の512語彙設定を使い、256 byte baselineと比較。
領域別に往復一致、bytes/token、tokens/文字、文書token長の中央値とp95、学習時間・メモリを記録。
512は既存の初期値で、日本語に最適とは仮定しない。
JSON・改行・インデントを含む全文でdecode(encode(text)) == textを確認する。

**TinyLM**：モデル規模、文脈長、seed、提示token数、学習時間、checkpointを固定して記録。
モデル規模と総学習量は計算環境を測って別仕様で決める。
領域別のdev損失、固定promptの生成、日本語のユーザー評価、数学の最終答一致を別々に見る。
Tokenizerの異なるモデル比較はtoken当たり損失だけで判断せず、bits/byteも使う。

**tool能力**：JSON解析率 → 引数適合率 → 実行成功率 → 最終課題成功率を分ける。
同じ課題でtoolあり/なしを比較し、記録内容を入れ替えた場合に応答が追随するかも調べる。
形式が正しいだけでは、道具を役立てた証拠にならない。

## 7. 凍結条件とv0.1

凍結時には本文hash一覧、出典、ライセンス、group/split、実配合、除外件数、seed、変換器版を保存する。
日本語原稿、整形器、重複検査、生成器、評価分割が揃うまで完成扱いにしない。
実験結果を残してからv0.1へ進み、最初は配合・資料・Tokenizerなど一つの要因を変える。
testを見て調整した場合はその事実を記録し、以後の最終判定には新しい保留課題を用意する。
