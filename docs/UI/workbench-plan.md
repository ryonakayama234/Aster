# Asterの学習・Agent作業画面

2026-09-20。Sitesの素材・Tokenizer画面を実装済み。保存bundleのブラウザ内読込・本文比較・BPE・考察保存が動く。
ローカルPython実行接続、TinyLM学習、Agent実行はまだ未実装。
Sites用のソースは `ui/` の独立したチェックアウト。親のAsterや原本データはSiteへ送らない。
参考は同フォルダのmain.pngとtool.png。掲載された数値・モデル名・epochは構想例で、実測値ではない。

## 目的

ユーザーが実行し、何が起きたかを観察し、原因の仮説を立て、次の実験を選べる画面。
「結果が出た」という通知に留めず、入力・処理・変化・出力へ戻れるようにする。
本文抽出・Tokenizerの段階から画面を使い、TinyLMの完成までUIを後回しにしない。

## 参考画像から引き継ぐ構成

- 左：素材／ことばを分ける／学習を観察する／比較と考察／道具と記録。
- 中央：操作対象と実際の結果。比較できるものを左右に置く。
- 右：観測、仮説、次に試すこと、ユーザーの考察メモ。
- 下：実行記録、入力と条件、対応するコード、実行中か保存記録の再生か。
- 色は濃紺・白を基調とし、青を主要操作に使う。装飾より読みやすい情報密度を優先。

各画面は実装した機能から順に公開する。未実装の操作を動くように見せない。

## 実装順

### 1. 本文抽出と観測記録

training-view-v0の抽出器と、UIからも読めるrun/eventsを作る。
最初の小さな対象で、原本・canonical・学習本文を結びつける。

### 2. Sitesの最初の画面：素材＋ことばを分ける

**素材**：ファイルを選ぶと、原本→canonical→学習本文の変化と、残した／除いた理由を見られる。
採用・保留、group、分割、本文bytes、出典が分かる。まずは実際の保存結果を読み込む画面から始める。

**ことばを分ける**：同じ文を文章→UTF-8 bytes→token IDsと追う。
merge規則を一つ選び、どの並びがまとめられたかを示す。固定したTokenizer版を表示する。
byte-level BPEのtokenは単独ではUTF-8文字として表示できない場合があるため、bytesと文中の対応を表示する。
decode時に置換文字へ変えた表示を、元のtokenの文字列と誤解させない。

この段階ではembedding・損失・学習曲線の実測値はまだない。架空の曲線で埋めない。

### 3. TinyLMの学習・比較を接続

同じ入力・Tokenizer版でcheckpointを切り替えて次token分布を比べる。
モデルの生の予測分布と、temperature等を適用した生成用分布を区別する。
checkpoint ID、step、見たtoken数を表示し、epochだけに依存しない。

文章→bytes→IDs→embedding→予測→損失→更新を追えるようにする。
embeddingは数値ベクトルとして形・一部の値・変化を確認し、次元に意味ラベルを勝手に付けない。
低次元に投影する場合は近似的な可視化だと示す。
学習実行と、保存済みの学習履歴を再生する操作は分ける。

右欄の「観測」は測定値に基づき、「仮説」は説明の候補として表示する。
train loss低下だけで賢くなったと判定しない。データ・モデル・予算の異なる比較も条件を表示する。
テスト用データを繰り返し見て調整したときは、最終評価とは区別する。

### 4. Agent使用＋道具と記録

計算器とmemory.put/getの小さな実行ループを接続する。
モデル出力→引数検査→実行器の観測→状態変更→次のモデル入力を時系列で示す。
最初の規則ベース方策は「ルール」、モデルが選んだ行動は「モデル」と表示する。

tool.pngで示すtotal=42の状態変更は、memory.putの**提案時ではなく実行完了時**に表示する。
calculatorの結果が42であることと、記憶へ42が保存されたことは別イベント。
実行成功・JSON適合・最終課題達成を別々に判定する。
記憶の値を変えて試す場合は元実行を改変せず、親runを参照する別実験にする。

## 共通する観測データ案

### Run

run ID、種別、入力artifact参照、recipe/code版、seed、状態、開始終了、出力artifact参照。
失敗や途中停止でも、成功したように表示せず最後の確定イベントまでを残す。

### Event

run ID、単調増加するseq、種別、生成者、時刻、入力出力参照、状態。
生成者はpipeline / trainer / model / executor / evaluator / user等。
並び順は時刻だけでなくseqを使う。イベントのschemaにも版を付ける。
大きな本文・重みを各イベントへ複製せず、版が固定されたartifactを参照する。

### Note

対象run・step・artifact、観測、仮説、次に試すこと、作成者。
測定ログの本文を上書きせず、考察を別記録にする。

初回に全イベント種別を実装しない。本文抽出のstart/sample_transformed/sample_deferred/completed/failedから始める。

## SitesとWSLの接続を段階的に作る

Sitesは画面、WSLのAsterはPythonの実行・データ・モデルを受け持つ案。
ホストされたSitesにローカルのファイルやGPUへ直接アクセスする機能があるとは仮定しない。

1. 最初は明示的に選んだrun bundleをブラウザで読み、実データの再生・比較を使えるようにする。
   ファイル選択はブラウザ内での読み込みを基本とし、原本全量のサーバー送信を前提にしない。
2. 実行ボタンをつなぐ段階で、Sitesの配信元とローカルサービス間の接続方式を小さく検証する。
   認証・許可するorigin・接続切れ・CORSやブラウザの制約を確かめる。ローカル中継方式はまだ未選定。
3. 接続できたら、許可したAster処理をジョブとして開始・停止し、run/eventsを受信する。
   UIから任意のshell文字列を実行する作りにはせず、recipeを選ぶ形式にする。

「保存結果を読む」段階を「Pythonを実行できる」完成版として扱わない。
公開する説明用sampleと、個人の原本・対話ログを分ける。
実際のサイト登録・実装・公開時はSitesのbuilding/hosting手順を使用する。

## 最初のUIの完了条件

- 実際の抽出runを開いて、どの本文がどの原本から来たか分かる。
- 保留理由と入力条件を見て、次に何を直すか判断できる。
- 選んだ文のbytes・token ID・復号を実際のTokenizer出力で確認できる。
- 実測値、未実装、保存再生、実行中の区別がつく。
- ユーザーの考察メモを対応するrunに紐づけて保存・再読込できる。
- ブラウザ表示の検証を行う。画面が表示できたことをローカル実行接続の検証と混同しない。
